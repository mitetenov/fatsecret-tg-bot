# 0003. Все запросы к FatSecret идут по OAuth 1.0, а не OAuth 2.0

Дата: 2026-07-30
Статус: принято

## Контекст

FatSecret предлагает две независимые схемы авторизации с **разными парами ключей**:

- **OAuth 2.0** — `client_id` / `client_secret`, токен через `client_credentials`.
  Именно её продвигает документация. Доступ ограничен набором scope
  (`basic`, `premier`, `barcode`, `localization`, `nlp`, `image-recognition`).
- **OAuth 1.0** — `consumer_key` / `consumer_secret`, подпись HMAC-SHA1 на каждый
  запрос. В документации выглядит легаси-путём.

Ключи одной схемы не работают в другой: попытка подписать запрос OAuth 1.0 ключами
OAuth 2.0 даёт `code 8: Invalid signature`, что легко принять за ошибку в алгоритме
подписи. Мы на это потратили один заход отладки.

Проверено на живом аккаунте:

1. **Дневника в OAuth 2.0 нет.** Среди scope нет ничего похожего на `profile`, а
   доступ к дневнику конкретного пользователя («signed and delegated requests»)
   документация прямо называет доступным исключительно через OAuth 1.0. Запись
   Позиций — суть этого проекта, значит OAuth 1.0 обязателен в любом случае.
2. **OAuth 1.0 умеет и чтение.** Двуногая подпись успешно выполняет `foods.search` —
   отдельная схема для поиска не нужна.
3. **IP Restrictions действуют только на OAuth 2.0.** Запрос по OAuth 2.0 с
   неразрешённого адреса возвращает `code 21: Invalid IP address detected`, тогда как
   подписанные запросы OAuth 1.0 этим не ограничены.

## Решение

Бот использует **только OAuth 1.0**: двуногую подпись для поиска продуктов и
трёхногую (с access-токеном пользователя) для дневника и Своих продуктов. Ключи
OAuth 2.0 в конфиге необязательны и нужны лишь диагностике — по выданным scope видно,
какой у аккаунта тариф.

## Последствия

- Одна схема авторизации на весь проект: один подписыватель, один набор ключей, одна
  ветка кода вместо двух.
- **Хостинг не привязан к IP.** Динамический адрес — не проблема, Raspberry Pi дома
  подходит наравне с VPS. Это прямое следствие пункта 3 выше.
- Подпись становится критическим кодом: она ломается тихо, поэтому живёт чистыми
  функциями и покрыта тестами по эталонному примеру RFC 5849 §3.4.1.
- Legacy `server.api` проверяет подпись по query string — запрос с параметрами в теле
  POST возвращает `Invalid signature`. Поэтому двуногие вызовы идут через GET.

## Когда это решение стоит пересмотреть

Если FatSecret объявит об отключении OAuth 1.0 либо добавит в OAuth 2.0 scope для
доступа к дневнику. До тех пор OAuth 2.0 не даёт нам ничего, кроме второй схемы
авторизации и зависимости от статического IP.
