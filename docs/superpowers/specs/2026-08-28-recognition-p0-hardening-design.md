# P0 Hardening распознавания

**Дата:** 2026-08-28  
**Статус:** одобрено для планирования

## Цель

Устранить четыре подтверждённых источника систематических ошибок без изменения
пользовательского сценария «реплика → черновик → явное подтверждение»: неверный
формат штрих-кода для FatSecret, неработающий fallback при синтаксически плохом
ответе LLM, принятие физически неправдоподобных КБЖУ и вычисление даты кнопками
«Сегодня/Вчера» в часовом поясе сервера.

В этот этап не входят телеметрия качества, новый ранжировщик Кандидатов, хранение
confidence, поддержка нескольких фотографий упаковки и переход на новые версии
поисковых методов FatSecret. Они остаются отдельными последующими этапами.

## 1. Штрих-коды

### Контракт

Внутреннее представление кода сохраняет цифры в исходной стандартной длине: 8,
12, 13 или 14. До любого внешнего поиска код обязан пройти проверку контрольной
цифры GTIN. Последовательность неправильной длины или с неверной контрольной
цифрой не считается товарным кодом.

Для FatSecret ввод нормализуется в GTIN-13:

- EAN-8 дополняется пятью нулями слева;
- UPC-A дополняется одним нулём слева;
- EAN-13 используется без изменения;
- UPC-E разворачивается в UPC-A по стандартным правилам с последующим добавлением
  нуля слева;
- GTIN-14 не отправляется в `food.find_id_for_barcode`, потому что метод принимает
  только GTIN-13.

Open Food Facts получает исходный валидный GTIN: его API не требует преобразовывать
EAN-8, UPC-A и GTIN-14 в один формат.

`pyzbar`-символики EAN, UPC и обычные линейные коды могут дать Кандидата. ISBN
отбрасывается как заведомо не относящийся к продуктам питания. Числовая строка из
QR или неизвестной символики используется только как fallback и только при валидной
контрольной цифре.

Если код валиден для Open Food Facts, но не представим для FatSecret, бот пропускает
поиск FatSecret и продолжает существующий OFF/LLM/photo fallback. Ошибка нормализации
не должна завершать весь сценарий.

### Границы изменений

Чистая GTIN-логика живёт в `src/fsbot/domain/barcodes.py`. Клиент FatSecret получает
уже нормализованное значение либо сам вызывает один явно названный доменный helper.
Привязки собственных продуктов продолжают использовать исходный валидный код, чтобы
повторное сканирование совпадало с тем, что отдаёт декодер.

## 2. Fallback LLM

### Контракт

HTTP 200 не означает успешное распознавание. Модель считается успешной только после
того, как её ответ прошёл `parse_recognition` и доменную валидацию.

Для каждой модели из настроенной цепочки выполняется:

1. запрос с `json_schema`;
2. парсинг результата;
3. при ошибке — одна repair-попытка той же модели без схемы с требованием вернуть
   валидный JSON;
4. при повторной ошибке — переход к следующей модели.

Ошибки HTTP, не-JSON envelope OpenRouter, пустые choices, неожиданный тип content и
ошибки парсинга агрегируются. `LLMError.rate_limited` остаётся истинным только тогда,
когда все реальные обращения завершились HTTP 429; синтаксически плохой ответ не
маскируется как rate limit.

Запросы с `response_format` включают `provider.require_parameters=true`, чтобы
OpenRouter не выбирал endpoint, игнорирующий structured output. Repair-попытка без
схемы не требует поддержки этого параметра.

Остальные методы (`translate_product`, web lookup штрих-кода) сохраняют текущий
fallback по транспортным ошибкам. Их предметная схема не смешивается со схемой
распознавания еды.

## 3. Проверка КБЖУ

### Контракт

Один общий чистый валидатор применяется и к LLM, и к Open Food Facts. Полный набор
КБЖУ принимается только при выполнении всех условий:

- все четыре значения являются конечными числами;
- калорийность больше 0 и не превышает 1000 ккал на 100 г;
- белки, жиры и углеводы находятся в диапазоне от 0 до 100 г на 100 г;
- энергетическая оценка `4 × белки + 9 × жиры + 4 × углеводы` не противоречит
  заявленной калорийности больше чем на `max(80 ккал, 35% заявленной
  калорийности)`. Допуск намеренно широкий: он учитывает округление и клетчатку,
  но отсекает грубые OCR-ошибки.

Энергетическая проверка предназначена для явных OCR-ошибок, а не для отбрасывания
необычных продуктов. Если энергетическая оценка макронутриентов меньше 1 ккал, эта
проверка пропускается: калории могут приходить из алкоголя или других не
представленных полей.

Невалидный профиль трактуется как отсутствие КБЖУ. Он не создаёт Свой продукт и не
участвует в сверке Кандидатов, но распознанное название и поиск FatSecret продолжают
работать.

В этом этапе база остаётся «на 100 г», как в текущей схеме. Поддержка отдельного
основания `per_100ml` требует изменения модели данных и будет отдельным этапом.

## 4. Дата кнопками «Сегодня/Вчера»

### Контракт

`shift_day` больше не использует `date.today()`. Базовая дата вычисляется через
существующий `daybounds.resolve(tz, now_utc)` и тем самым учитывает пользовательский
IANA timezone и начало пищевых суток в 04:00.

- «Сегодня» означает текущую дату Дневника по правилам проекта;
- «Вчера» означает предыдущую дату относительно текущей даты Дневника;
- неизвестный hint не меняет черновик;
- тесты могут передать фиксированный `now_utc`, production использует текущее время.

Callback получает timezone связанного пользователя; при отсутствии индивидуального
значения используется `Config.default_tz`. Изменение не затрагивает первоначальное
автоопределение даты в `build_draft`.

## Ошибки и пользовательский интерфейс

Новые проверки не добавляют новых обязательных вопросов пользователю. Невалидный
штрих-код идёт по существующему фото-сценарию, невалидные КБЖУ отключают только кнопку
создания продукта, а исчерпание LLM-цепочки показывается через существующий обработчик
`LLMError`.

Тексты карточек и callback_data остаются совместимыми с уже сохранёнными черновиками.

## Тестирование

Разработка ведётся через TDD. Обязательные регрессии:

- валидные EAN-8, UPC-A, EAN-13 и UPC-E превращаются в ожидаемый GTIN-13;
- неверная контрольная цифра, ISBN и неподдерживаемый для FatSecret GTIN-14 не уходят
  в его API;
- невалидный ответ первой модели приводит к вызову второй;
- repair-попытка может спасти текущую модель;
- `require_parameters` присутствует только в schema-запросе;
- NaN, infinity, отрицательные и невозможные КБЖУ отклоняются одинаково для LLM и
  Open Food Facts;
- обычные и округлённые этикетки принимаются;
- кнопки даты используют timezone пользователя и границу 04:00;
- полный существующий набор тестов остаётся зелёным.

Для HTTP-кода применяются управляемые fake transport/клиенты; тесты не обращаются в
сеть. Финальная проверка включает полный `pytest`, `compileall` и сборку Docker test
stage, если она доступна в текущем окружении.

## Критерии готовности

1. FatSecret никогда не получает ненормализованный либо невалидный GTIN.
2. Синтаксически плохой ответ основной модели действительно активирует следующую
   модель после одной repair-попытки.
3. LLM и Open Food Facts используют одну и ту же проверку правдоподобия КБЖУ.
4. Ручной выбор даты не зависит от timezone процесса или сервера.
5. Существующие пользовательские сценарии и сохранённые черновики не требуют
   миграции.
